# 收尾提示延迟排查与修复（2026-11-25）

## 实机记录

对局 `run-20261125-224229` 的高分存档在 22:44:45.716 完成，轨迹保存耗时 0.468 秒。
自动录制器于 22:44:53.060 才写入 `run_finished`，比存档晚 7.344 秒。
其对应第 254 帧的日志如下：

| 环节 | 耗时 |
| --- | ---: |
| 获取截图 | 7.740 秒 |
| 识别 | 0.398 秒 |
| 录制器处理 | 0.0015 秒 |

录制器需要连续帧确认终局，其状态灯等待下一张确认帧；高分库已保存并不代表这张确认帧已经返回。

## 发现的阻塞链

`default_auto_capture()` 查找游戏时枚举所有窗口，原先先读标题、再读进程 ID。
Windows 对同进程窗口的 `GetWindowTextLengthW/GetWindowTextW` 会向所属线程发送同步消息。
当采集线程枚举到助手自身的 Tk 窗口，若界面线程正在处理长回调，采集也会跟着等待。

用独立进程创建一个屏外 Tk 窗口，故意让其界面回调忙 0.8 秒，同时运行项目的真实
`find_capture_window()`：修改前耗时 **0.8068 秒**，修改后 **0.0074 秒**，两次均找到游戏。
复现脚本保存在 `runtime/finish_latency_investigation/probe_window_lookup.py`。
这是受控复现，证明了该阻塞路径；历史 7.74 秒没有原生调用堆栈，不能断言其中每一毫秒都由此产生。

另有两处会放大等待：

- 自动截图降级时重新调用 `capture_target()`，重复两次窗口枚举和已经失败的内容抓取。
- 收尾后统计更新调用 `_refresh_after_correction()`，即使记录模式开启或本局已结束，也会在界面线程计算推荐。

## 修改

- 游戏窗口搜索先查进程 ID，在读取标题和几何前跳过助手自身进程。诊断用的完整窗口枚举仍可保留自身窗口。
- 自动截图降级直接截取这一帧已经选定的游戏窗口区域；保留每帧窗口尺寸读取及识别前后几何校验，不缓存旧坐标。
- 统计刷新及人工纠错刷新遵守记录模式，已结束的对局不再计算推荐。
- 成功存档后立即唤醒采集线程取得确认帧。
- 在录制器尚未确认时，状态灯明确显示“本局已存档 · 录制收尾确认中”；连续帧防误判与截图错误提示继续保留。
- 帧性能记录新增 `capture_stages`，分别记录窗口搜索、窗口内容抓取、前台检查、区域截图和总耗时。后续慢帧可继续追到具体阶段。

## 第二次实机反馈：存档后仍等 5.85 秒

23:14 这一局，存档在 23:14:20.708 完成，录制器在 23:14:26.555 确认结束。
确认帧截图只用 0.325 秒，识别调用的墙钟耗时却为 5.968 秒，`full_refresh=0`。
代码没有要求终局重新做一次耗时 5 秒的完整识别。

受控复现：固定使用 `runtime/category_investigation/game_visible.png`，在同一个
`VisionTracker` 上连续识别，再同时启动真实历史数据的 `_build_complete_stats()`。
平时识别 0.266–0.327 秒；统计线程启动后，同一张图的识别变成 6.469 秒，统计耗时 6.453 秒。
性能分析显示几乎全部统计开销在 `_deduplicated_runs()` 调用 `normalize_run_payload()`：
它在去重之前深复制了完整历史轨迹、重新构造每一步的决策，而风险报告只读对局摘要。
这些 CPU 工作与识别共享 Python 进程，识别计时包含被争抢的执行时间。

修复：风险统计先按原有优先级、时间戳选择每局记录，再仅生成统计需要的字段。
完整轨迹导出和落盘规范化保持原实现，历史文件未被改写。

复测结果：

| 相同截图与历史数据 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 后台统计耗时 | 6.453 秒 | 0.273 秒 |
| 与统计同时进行的识别 | 6.469 秒 | 0.445 秒 |

统计不修改输入，以及不复制完整历史、不重建决策。
